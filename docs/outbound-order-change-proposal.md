# 出库订单变更校验想法（暂不开发）

讨论日期：2026-10-14

## 当前决定

这是低频场景的后续开发想法，目前暂缓。当前优先检查扫码出库单号后的订单加载速度。本文件仅记录方案，不代表功能已实现，不执行删除或新增业务表。

## 业务场景

- 原 ERP 出库单反审后修改物料或需求数量。
- ERP 单号按区段顺排，删除单据后，号码可能被原客户或另一客户重开的单据复用。原客户重新开单也可能变为后续号码。
- 当前本地历史主要按单号和仓库关联，缺少持久化的 ERP 单据身份对比。相同号码复用时，需要防止沿用旧扫码，或改写旧客户。

## 倾向的处理规则

1. 每张订单保存一份已确认的 ERP 精简资料：账套、单据类型、内部 ID、单号、客户身份、仓库，以及按存货编码汇总的需求数量。
2. 再次取得同一账套、同一单号的 ERP 数据时，先比较旧资料，随后更新。比较的是两次 ERP 数据；部分扫码与 ERP 总需求不相等，是正常情况。
3. 内部 ID 或客户、仓库、物料清单、各物料需求数量等关键资料改变时，倾向清空旧单有效扫码数据、释放旧记录造成的追溯码占用、重新扫码，不做旧记录迁移或重新关联新单。
4. 资料未变时保留扫码进度，继续操作。正常从 A 单切换 B 单不触发删除 A 单。
5. ERP 查询失败、字段缺失或历史身份未知时，不据此判定变更并删除。

## 存储及速度想法

- 拟在 PDA 现有本地 `palm_warehouse_v2.db` 内增加精简资料表，每单一份最新确认资料；不重复保存每次读取，也不保存完整 ERP 原始响应。
- 用账套和单号的索引定位资料，复用现有 ERP 查询结果进行比较；普通物料扫码使用当前单内存状态，资料未变不重复写库。
- 完整数据库备份应包含这张资料表。旧数据库缺少资料时需要兼容，不能直接认定当前同号单就是原单。

## 实施前待确认

- 尚无可靠证据保证当前 T+ 版本的内部 ID 在反审修改时不变、删除重建时必变且不复用；需要厂家定义或测试账套变更前后样本。多项内容校验可减少漏判，但所有返回字段均完全相同时无法单凭内容识别删除重建。
- 删除必须按旧身份对应的记录范围执行，不能混删同号新单。
- 普通有效扫码删除后，现有回收站不参与重复码拦截；其他仍有效记录的占用要保留。
- 存在销售退货或拆包生成标签被其他订单使用时，需保留现有依赖检查，避免破坏关联；原纸质标签及已发走实物不能随数据库删除自动撤回。
- 清空还需处理旧队列、缓存、相关标签任务和请求生命周期，防止旧请求重新写入。
