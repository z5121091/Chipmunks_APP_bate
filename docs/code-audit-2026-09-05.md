## 1. P2：较旧的并发响应会覆盖刷新后的新缓存

- 位置：`server/src/erp.ts:1364`、`server/src/erp.ts:1406`；代理层 `server/src/index.ts:921` 也无响应新旧顺序检查。
- 普通请求和 `bypass` 刷新请求使用不同的进行中请求键，可以同时访问上游，但最终写入同一个缓存键。
- 当旧请求较慢、新刷新较快时，新数据先缓存，旧数据随后覆盖它；之后的普通查询会再次拿到旧数据。
- 本地实际复现：普通请求保留旧数量 100 暂不返回；刷新请求返回新数量 200 并显示 `REFRESH`；释放旧请求后，再查询命中 `HIT`，数量变回 100。模拟上游共收到 2 次请求。
- 建议：对同一查询键设置刷新代次或请求顺序，只有仍有效的响应可以写缓存；同时覆盖代理层。补充“旧请求后返回”的回归测试。
- 当前测试中的“同模式并发合并”通过，但不包含这种普通查询与强制刷新交错的情况。

## 2. P2：两层缓存可能延长同一份数据的实际存活时间

- 位置：`server/src/index.ts:714`、`server/src/index.ts:921`；`server/src/erp.ts:31`、`server/src/erp.ts:1346`。
- 代理与 ERP 层都设置单据 5 分钟、库存 15 秒等缓存策略。代理收到成功结果后，无论结果是否命中 ERP 层旧缓存，都会从当前时刻重新计算完整 TTL。
- 触发条件：代理缓存被淘汰、代理重启或另一个代理首次访问，而 ERP 层缓存仍有效。
- 例如 ERP 层的单据缓存只剩 1 秒，代理取得该旧值后又保存 5 分钟。此时同一份数据可接近 10 分钟未更新，并非约定的单层 5 分钟。这是基于实际两层缓存代码推导的边界，不表示每次查询都会发生。
- 强制 `bypass` 请求可以绕过缓存；本项针对普通读取，不应误认为所有刷新按钮都会返回旧数据。
- 建议：先明确缓存归属。最小做法是保留一个权威缓存层，或让代理遵守上游剩余有效期。不要简单加长 TTL 来追求响应速度。

## 3. P2：代理备用地址重试重新获得整段超时预算

- 位置：`server/src/index.ts:634`，尤其 `648`、`669`；默认超时定义于 `150`；客户端 `client/utils/backendApi.ts:58`。
- 域名请求与备用 IP 请求分别创建新的 `AbortSignal.timeout`，默认各 22 秒。极端情况下两段可以接近 44 秒。
- 客户端默认 25 秒就中断，因此第一段接近超时后才启动备用请求时，备用请求往往还没来得及完成，APP 已提示失败。
- 这与客户端注释“等待服务端返回结构化错误”的目标不一致，也会让后端在客户端离开后继续处理无用查询。
- 本项由代码中两次独立预算确认；未人为向正式服务器制造超时。
- 建议：整次代理请求共用总截止时间，备用地址只使用剩余时间；将客户端断开传播到下游。保留扣子环境需要的备用地址，不删除其回退能力。

## 4. P2：采购入库的长错误提示横向溢出

- 位置：`client/screens/purchase-receive/styles.ts:57`、`71`；呈现位置 `client/screens/purchase-receive/index.tsx:740`。
- 本地隔离浏览器禁止访问外部网络，触发带完整接口 URL 的真实前端错误文案。
- 320 像素宽视口中，文档被撑到 363 像素；360 像素视口中被撑到 395 像素。错误文字超出右边界，后半段无法正常阅读。浅色和深色均复现。
- 建议：错误文案区补齐可收缩约束及长连续字符串换行；默认显示简短中文说明，接口完整地址放入可展开的诊断内容。
- `stock-query/styles.ts:154` 的错误布局与之相近，应同时回归，但本次没有把它列为已经复现的相同 BUG。

## 5. P2：规则编辑页重复处理顶部安全区，滚动容器责任不清晰

- 位置：`client/screens/rules/index.tsx:559`、`560`；`client/components/Screen.tsx:242`。
- 外层 `Screen` 默认已加 `insets.top`，内部编辑容器又加一次 `paddingTop: insets.top`。非零安全区设备上，同一顶部空间会被重复计算。
- 该编辑页使用 `KeyboardAwareFormScrollView`，但 `Screen` 的自动识别只认识原生 `ScrollView/FlatList/SectionList`，可能再套一层滚动容器。相关位置：`Screen.tsx:202`、`247`，规则编辑页 `568`。
- Web 的顶部安全区为 0，不能用 Web 正常来排除这项 PDA 布局风险。本项确认的是重复的代码路径，未声称已在真机测得偏移像素。
- 建议：页面明确拥有自己的滚动容器，使用现有 `disableAutoScroll`；顶部安全区只交给一层处理。修改后检查弹窗键盘、保存按钮、上下留白。

## 6. P2：默认前端 lint 没有覆盖主要业务实现目录

- 位置：`client/package.json:11`。
- 本次 `pnpm -w lint:all` 通过，但实际执行的 Expo lint 命令只包含 `client/app` 与 `client/components`；页面实际实现位于 `screens`，解析和数据库实现位于 `utils`。
- 显式补查 `screens hooks utils contexts constants`，扫描 104 个文件，得到 56 条错误级诊断、117 条警告。
- `database.ts` 占 43 条错误、88 条警告；其余涉及正则写法、控制字符处理、Hook 依赖、未使用代码等。控制字符正则在扫码处理中可能有业务必要性，不能为了清零直接删除。
- TypeScript 与运行测试通过，不等于 ESLint 覆盖完整。诊断数量也不等于业务 BUG 数量。
- 建议：把业务目录加入固定校验命令，分类处理已有诊断。对确有必要的扫码控制字符规则使用有理由的局部说明，不全局关闭规则。优先处理会影响行为的 Hook 依赖和危险解析路径。

## 7. P3：统一了输入框外观，但扫码生命周期逻辑仍分散维护

- 位置：`client/screens/inbound/index.tsx:1054`、`client/screens/inventory/index.tsx:724`、`client/screens/outbound/index.tsx:2575`；库存查询与采购单录入也各自管理提交计时器。
- `WarehouseScanInput` 已统一外观，多个页面仍各自实现防抖、回车与按钮提交、清空输入、扫码队列、失焦恢复、离页计时器清理。
- 入库和盘点尤其接近。后续修复某一种提交时序时，需要同步核对多个页面，容易出现“一个模块已修、另一个遗漏”。
- 当前未把这些重复本身认定为丢扫码 BUG；现有输入处理相关测试通过。
- 建议：只提取确定共用的输入提交与计时器清理部分，并保留各页面业务处理器。出库的订单快速提交、拆包期间暂停队列与入库批量刷新并不相同，不应强行合并为一套业务流程。

## 8. P3：旧 UI 组件和页面样式存在未使用残留

- `client/components/UiRedesign.tsx:415` 的 `UiScanBox` 与 `client/components/ScanWorkflowPanel.tsx:30` 目前在 `client` 中仅有定义，没有调用点。

- 它们不直接造成业务错误，但增加查找和维护成本，且容易让以后新增页面误用旧输入样式。
- 建议：确认引用后删除残留组件及只由这些组件使用的样式，保留当前生效的 `WarehouseScanInput`。不要因为文件较长就一次重写数据库或整个扫码页面。

## 建议处理顺序

1. 缓存新旧覆盖与缓存有效期，先保证数量与单据读取一致性。
2. 全链路总超时，保留开发/扣子代理回退并减少无效等待。
3. 长错误布局、规则编辑页安全区与滚动责任。
4. 补齐校验范围，再做有针对性的重复逻辑和废弃代码清理。

已有连接复用和同模式请求合并应保留。本次本地模拟耗时不能代表真实 ERP 延迟，不能据此承诺首次查单达到毫秒级，也没有证据把当前延迟直接归咎于服务器配置。
