# 掌上仓库全覆盖静态代码审查

审查日期：2026-07-11  
审查范围：Express 后端、Expo 全部业务页面、UI 组件与设计令牌、expo-sqlite、Excel/NAS/同步助手、Android 原生备份与工程结构。  
审查方式：只读静态审查；未编译、未启动服务、未调用 ERP、未修改业务源码。  
对照资料：`docs/ui-preview/warehouse-ui-redesign-preview.png`、`docs/ui-preview/ui-assets-contact-sheet.png`。

## 1. 总体结论

项目已经具备扫码出库、ERP 采购入库、库存查询、盘点、拆包、Excel 同步和数据库备份的完整业务骨架，关键流程并非“不可用”。但正式环境上线前仍有一组必须优先处理的问题：

1. 双账套后端默认共用同一个令牌状态文件，存在跨账套覆盖风险。
2. ERP 业务接口和同步上传接口目前没有有效访问鉴权，管理接口在非 `production` 且未配置密钥时会放行。
3. 盘点整包与拆包草稿可能被重复保存为新盘点单。
4. ERP 入库单号 `II-*` 仍按旧 `RK-*` 规则生成 Excel 文件名，多个单据可能覆盖同一文件。
5. Android 后台备份复制活跃 SQLite 文件，且成功签名取自上传后的实时数据库，不能证明上传文件与当前签名一致。
6. 数据库恢复流程在重新初始化完成前删除回滚副本，迁移失败时可能无法恢复原数据库。
7. Expo 云构建与本地 Android 工程的包名不一致，会形成两个应用，无法正常覆盖升级或继承同一应用数据。
8. 业务表没有持久化 `erp_account_key/org_id`，历史数据所属账套依赖仓库名称或单号位数推断，不满足正式双账套审计要求。

建议当前测试可以继续，但正式迁移、双账套启用和 APK 发布前，至少完成本文 P0 及核心 P1 修复。

## 2. 严重度定义

- **P0 阻断级**：可能导致数据丢失、跨账套、错误覆盖、正式环境未授权访问或 APK 升级断裂。
- **P1 高风险**：可能造成业务数据错误、ERP 配额浪费、单据状态不一致或备份不可恢复。
- **P2 中风险**：主要影响可维护性、稳定性、交互明确性或性能。
- **P3 改进项**：不直接破坏业务，但会增加长期维护成本或视觉漂移。

## 3. P0 阻断级问题

### P0-1 双账套共享令牌状态文件

**证据**：`server/src/erp.ts:146-148` 默认把状态写入 `<cwd>/sync-data/chanjet-state.json`；路径未包含 `CHANJET_ACCOUNT_KEY`。`server/.env.example:22-23` 也没有要求每个账套配置独立目录。

**影响**：同一台服务器从同一项目目录启动 A、B 两个 Node 进程时，`appTicket`、`openToken`、`orgId`、消息状态会互相覆盖，可能用无锡笃能的界面查询上海花栗鼠，或反向污染授权。

**建议**：默认路径改为 `sync-data/<accountKey>/chanjet-state.json`；状态文件保存并校验 `accountKey`；生产启动时若账号、域名、状态目录不完整或重复，直接拒绝启动。两个账套使用独立 Linux 用户、环境文件、端口、日志和状态目录。

### P0-2 ERP 与 Excel 上传接口缺少有效鉴权

**证据**：`server/src/index.ts:243-245` 明确将 `requireBackendAccessKey` 定义为空操作；`server/src/index.ts:608-629` 的 ERP 中间件只校验账套标识并限流；`server/src/index.ts:999-1003` 的上传接口也使用空鉴权。

**影响**：知道域名的人可消耗 ERP 月度调用额度、探测业务数据，或向服务器持续上传/覆盖 Excel 文件。仅靠 CORS 不能阻止 APK、脚本和服务端请求。

**建议**：不要重新使用可从 APK 提取的 `EXPO_PUBLIC_*` 固定密钥作为唯一防线。正式版应采用短期设备会话令牌、服务端签名或反向代理/VPN 鉴权，并按设备、账号、接口分别限流。上传接口还应增加文件哈希、请求幂等键和用户/设备审计。

### P0-3 管理接口在环境变量缺失时可能失守

**证据**：`server/src/index.ts:154-166` 仅在 `NODE_ENV === 'production'` 时因未配置密钥返回 503；其他环境直接放行。`server/.env.example:13` 默认 `BACKEND_ADMIN_KEY` 为空。

**影响**：ECS/PM2 若漏配 `NODE_ENV`，授权、令牌等管理接口可能在公网无鉴权开放。

**建议**：管理接口始终 fail-closed；只有显式的本机开发开关才能放行，并限制为 loopback。启动时强制校验管理密钥强度。

### P0-4 盘点整包与拆包草稿会重复入账

**证据**：`client/screens/inventory/index.tsx:923-950` 保存时合并整包和拆包两类草稿；成功后 `:1035-1039` 只清理当前 `checkType` 的草稿。

**影响**：另一类型已经保存的草稿仍保留，下次确认会再次生成一个新 `PD-*` 盘点单，造成库存重复。

**建议**：批量写入和两类草稿清理放入同一个逻辑事务；只有两类草稿都清理成功才显示完成。保存请求增加草稿批次 ID/幂等键，避免重复点击或恢复后重复提交。

### P0-5 ERP 入库 Excel 文件名可能互相覆盖

**证据**：`client/utils/inboundExport.ts:39-44` 仍通过 `getExportInfoFromDocumentNo(inboundNo, 'RK')` 解析旧单号；当前 ERP 单据使用 `II-2026-...`。

**影响**：解析失败后会回落为当前日期和默认序号，不同 ERP 入库单可能写到同一个 `入库单_<仓库>_<日期>_01.xlsx`，后一次覆盖前一次。

**建议**：文件名直接包含经过安全清洗的 ERP `voucherCode`，例如 `采购入库_无锡笃能_II-2026-06-08-001.xlsx`；不要再生成 RK 序号。数据库、记录页、同步状态和导出文件统一使用 ERP 单号。

### P0-6 Android 自动备份快照与签名不一致

**证据**：`AutoDatabaseBackupWorker.kt:368` checkpoint 后，`:471-476` 直接 `File.copyTo` 复制活跃数据库；`:382-383` 上传后却对实时 `databaseFile` 调用 `markSuccess`，`:118-125` 保存实时文件的大小、时间和签名。

**影响**：checkpoint 与复制之间仍可发生写入；上传期间发生的写入可能进入“成功签名”但不在已上传文件中。系统会误判最新数据已备份，并跳过下一次备份。

**建议**：使用 SQLite backup API 或在应用统一数据库写锁下生成快照；对实际上传的快照文件计算 SHA-256，并把该哈希作为成功依据。上传成功后再原子更新备份状态。

### P0-7 数据库恢复过早删除回滚副本

**证据**：`client/utils/database.ts:9142-9146` 在关闭恢复后的数据库前删除 `.backup`；`:9190-9192` 的 `initDatabase()` 和迁移又发生在回滚副本删除之后。

**影响**：关闭数据库、重新打开或迁移失败时，原数据库副本已经消失，外层异常处理无法完成承诺的回滚。

**建议**：保留回滚文件直到恢复库完成完整初始化、迁移、完整性检查和最小业务查询；任何一步失败都用副本恢复。最终成功后再删除副本，并保留一份带时间戳的人工恢复备份。

### P0-8 云构建与本地构建包名不一致

**证据**：`client/app.config.ts:38` 为 `com.chipmunks.traceabilityBeta`；`client/android/app/build.gradle:107,109` 为 `com.chipmunks.traceability`。

**影响**：扣子/Expo 云构建和本地原生构建会安装为两个应用，不能覆盖升级，也不会读取相同 SQLite 和 SharedPreferences。用户会误以为数据丢失。

**建议**：确定唯一正式包名并同步 app config、Gradle、Kotlin 包路径、签名证书、EAS/云构建配置。发布前验证旧 APK 到新 APK 的覆盖升级及数据库迁移。

### P0-9 历史业务数据没有账套归属字段

**证据**：`client/utils/database.ts:3228-3408` 的出库、入库、盘点、拆包等核心表没有 `erp_account_key`、`org_id` 或 ERP `voucher_id`。当前账套由单号末段位数或仓库名称推断。

**影响**：仓库改名、编号规则变化、两家公司出现相同单号时，历史数据会被错误归类；导出和同步也无法提供可靠账套审计链。

**建议**：新增不可变的 `erp_account_key`，ERP 单据同时保存 `org_id/voucher_id/voucher_code`。新记录写入时固定账套；旧数据迁移时按当前规则回填并标记 `account_inferred=1`。

## 4. 后端审查

### 4.1 多账套与正式迁移

1. **P1：前端 URL 是编译时配置。** `client/utils/erpAccounts.ts:23-45` 依赖 `EXPO_PUBLIC_*` 域名和启用标志，正式换域名通常需要重打 APK。建议从一开始使用稳定二级域名，例如 `erp-a.example.com`、`erp-b.example.com`，迁移只改 DNS/Nginx，不改 App。
2. **P1：账套选择过度依赖单号位数。** `client/utils/erpAccounts.ts:58-65` 使用末段 3 位=无锡笃能、2 位=上海花栗鼠。该规则可作为首次路由线索，但查询返回后必须用 `orgId/accountKey` 校验。
3. **P1：缺少预期组织绑定。** 后端能返回 token 的 `orgId`，但没有强制与本进程的预期组织一致。建议增加 `CHANJET_ORG_ID` 并在授权、消息、每次请求前校验。
4. **P2：Coze 代理模式由环境痕迹推断。** `client/utils/backendApi.ts:11-13` 根据 `EXPO_PUBLIC_COZE_PROJECT_ID` 推断代理路径，容易因云构建环境变化产生 404。应使用显式 `EXPO_PUBLIC_BACKEND_MODE=direct|coze-proxy`。
5. **推荐部署结构**：一台 ECS 足够。Nginx 443 上配置两个二级域名；分别反代到 Node A/Node B 端口。每个进程拥有独立 `.env`、状态目录、日志目录、账号标识和服务用户。网站和 ERP 数据库可以共机，但必须隔离端口、账号、目录、资源限额与备份策略，ERP 数据库不应暴露公网。

### 4.2 令牌、缓存与接口逻辑

1. **P1：环境令牌永久优先于刷新令牌。** `server/src/erp.ts:606-612` 的优先级为环境变量、请求头、状态文件；`:761-774` 在环境变量存在时也会弱化过期判断。只要 `.env` 留着旧 token，刷新后保存的新 token 就永远不会生效。建议环境令牌仅作首次引导，运行时以验证过的状态令牌为准。
2. **P1：调用者可注入 token/SID。** `server/src/erp.ts:608-619` 接受 `x-chanjet-open-token` 等头；公网业务路由又没有真实身份验证。正式环境应禁止客户端覆盖后端凭据。
3. **P1：缓存键没有完整隔离凭据与组织。** `server/src/erp.ts:674-676` 的缓存键主要是 path/body；外层缓存虽含 account，但仍不含 org/token。错误凭据或另一个组织的结果可能污染缓存。缓存键至少包含服务端 accountKey + orgId + 规范化请求体。
4. **P1：应用级错误也可能被缓存。** 代理只按 HTTP 成功判断，畅捷通 HTTP 200 但业务 `code != 200/success=false` 的响应也可能进入缓存。只缓存明确成功且结构符合预期的响应。
5. **P1：缓存绕过可被公网调用者触发。** `X-Erp-Cache-Mode` 可控制 bypass，会直接增加月度额度消耗。该能力只应提供给受信管理请求。
6. **P2：ERP 请求通过外部 curl 进程实现。** `server/src/erp.ts:511-563` 每次 `spawn(curl)`；敏感请求头可出现在进程参数中，并带来进程启动开销、外部依赖、无响应体大小上限和客户端断开后仍继续执行的问题。建议改用 Node `fetch/undici`，设置连接/响应超时、body 上限和 AbortSignal。
7. **P2：列表参数上限不足。** `server/src/erp.ts:458-465` 只要求 `pageSize > 0`，没有最大值；`selectFields` 的数量和内容也未做白名单限制。建议限制页大小、字段数量、字符串长度和嵌套深度。
8. **P2：全局 JSON 上限 50MB。** `server/src/index.ts:631-632` 对所有 JSON/form 路由生效，公网消息或 ERP 路由可被大请求拖垮。按路由设置 64KB/1MB 等合理上限，Excel 使用独立流式限制。
9. **P2：上游错误详情直接返回。** `server/src/erp.ts:636-650` 可能把畅捷通原始响应返回给客户端。生产应返回稳定错误码和 requestId，详细内容仅写脱敏日志。
10. **P2：OAuth state 未形成完整防重放链。** 授权入口和回调需要生成、持久化、单次消费 state，并限制回调 code 的展示。

### 4.3 消息订阅与同步

1. **正向项**：默认拒绝明文消息，订阅消息使用加密校验；状态写入采用临时文件和备份，方向正确。
2. **P1：明文开关缺少生产保护。** `server/src/erp.ts:291` 允许环境变量开启明文消息；生产启动应在该值为 true 时直接失败。
3. **P1：采购入库状态的事件时序容错过宽。** 时间戳缺失/格式异常时可能覆盖已有新状态，旧消息重放会让已审核单重新显示。应优先使用平台消息 ID 去重，再以可验证的事件时间单调更新。
4. **P2：缺少 orgId 的消息可能被前端状态查询过滤。** 需要在解密后从可靠字段补齐组织并做账套绑定，无法确认组织的消息进入隔离队列而非业务状态。
5. **P2：消息状态仍是单 JSON 文件。** 两账套和长期运行后建议改为轻量 SQLite/Redis 表，至少建立 messageId 唯一键、voucherCode+accountKey 索引和保留期限。

## 5. Expo 前端业务逻辑审查

### 5.1 扫码出库

1. **P1：ERP 恢复失败后会降级成不受 ERP 明细约束的本地扫描。** `client/screens/outbound/index.tsx:1217-1280` 清空 `activeErpVoucher` 但保留活动订单，后续物料绕过 ERP 数量与明细匹配。应显式进入“ERP 未验证、禁止继续”状态；若要离线放行，必须由用户确认并记录原因。
2. **P1：销售出库单状态被解析但未校验。** `client/utils/erpSaleDispatch.ts` 返回 voucher 状态，却未阻止作废/不允许出库的单据。应建立可接受状态白名单。
3. **P1：12 小时 ERP 单据缓存缺少陈旧提示。** 缓存节省额度是合理的，但作废、修改数量或客户后仍可能继续使用旧数据。界面应展示“缓存于 HH:mm”，最终保存前只对该单据做一次条件刷新，或利用订阅消息主动失效。
4. **P1：出库列表/导出过滤包含旧 inbound 数据。** `client/screens/outbound/index.tsx:499-500` 仅排除 inventory；`client/utils/database.ts:4673-4679` 还兼容带订单号的旧 inbound。历史入库行可能出现在出库统计和导出中。建议完成一次数据迁移后只接受明确 `operation_type='outbound'`。
5. **P1：拆包不是一个端到端原子动作。** 页面先添加物料，再写拆包记录；进程崩溃在两次提交之间时会留下完整数量但无拆包标签。应由数据库层提供单一事务函数，完成物料、原/剩余标签、打印任务和订单数量更新。
6. **P1：订单管理可直接编辑拆包物料数量。** `client/screens/orders/index.tsx:940-973` 只改 material，不同步 unpack 记录与标签数据。应禁止通用编辑拆包行，或提供专用事务化更正流程。
7. **P2：订单页加载仓库有时序竞争。** `client/screens/orders/index.tsx:653-710` 的按单号加载 effect 未依赖已加载的 `currentWarehouse`，首次进入可能查错/空仓库且不会自动重试。
8. **正向项**：型号+版本绑定、ERP 明细累计、超量拆包入口和扫码声音反馈的总体方向正确；直接扫码入库前的落库错误已能反馈给用户。

### 5.2 采购入库

1. **P1：缺失数量被默认为 1。** `client/screens/inbound/index.tsx:684-688` 将空数量转成 `'1'`。标签解析错误时会静默多入 1 件。必须把数量设为必填，缺失或非正整数时语音+弹窗拒绝。
2. **P1：最终确认没有强制验证最新 ERP 明细。** 本地可使用最长 12 小时详情缓存，最终保存前不确认数量/状态是否变化。建议仅在点击完成时执行一次带 ETag/版本或 bypass 的单据刷新；失败则保留草稿，不落正式记录。
3. **P1：已入库判断仍依赖仓库名称。** 采购单本地完成状态按 voucherCode+warehouseName 判断。正式双账套应按 accountKey+voucherId/voucherCode 判断。
4. **P2：无效数量只写日志。** `client/screens/inbound/index.tsx:717-726` 直接 return，无视觉和语音提示。出库、盘点也有同类分支，应统一走 `feedbackInvalidQuantity`。
5. **P2：供应商一致性分支在 ERP 模式基本不可达。** 页面要求先选 ERP voucher，后续却只在 `!activeErpVoucher` 时检查供应商，说明旧本地流程残留。应删除死分支或明确两种模式。
6. **按用户确认保留**：未审采购入库单只取前 100 条，本轮不列为缺陷。

### 5.3 盘点与库存查询

1. **P1：盘点绑定遗漏版本号。** `client/screens/inventory/index.tsx:678` 只用型号查存货编码，可能把同型号不同版本匹配到通用/错误编码。应与入库、出库统一传入 version。
2. **P1：盘点草稿自动保存存在写覆盖竞争。** `client/screens/inventory/index.tsx:296-330,452-468` 使用异步读-改-写，effect 不等待前一次完成；快速连扫或切换类型时，较旧任务可能最后写入并覆盖新草稿。应使用串行队列、版本号 compare-and-set 或直接 SQLite upsert 草稿表。
3. **P1：盘点单号生成失败时返回固定 `001`。** `client/utils/database.ts:6926-6945` 把数据库错误吞掉并返回 `PD-<date>-001`。应 fail-closed，不能在单号分配失败时继续保存。
4. **P2：清空盘点没有确认且未等待持久层。** `client/screens/inventory/index.tsx:1053-1060` 立即提示成功，即使清理失败。应确认、await，并在失败时恢复界面数据。
5. **P1：现存量响应递归找数组可能拿错数据。** `client/utils/erpCurrentStock.ts:94-126` 在预期 `Rows: []` 时继续搜索其他数组；结果也未强制过滤为请求的 inventoryCode。应只接受已知响应 schema，并按账号+编码严格过滤。
6. **P2：库存页用第一行决定规格型号。** 多仓库返回顺序不稳定时，展示的型号可能来自非目标行。先按存货编码归一化，再从一致数据中取规格。
7. **正向项**：库存缓存包含账套和编码；切换账套会清空结果；未开放账套可以禁用输入并避免请求 ERP。

### 5.4 规则、绑定、仓库与设置

1. **P1：规则“条件”实际更像优先级而非硬约束。** `client/utils/database.ts:8027-8165` 即使供应商/关键字条件不满足，也可能把规则加入精确候选并最终选中。条件不满足时应彻底排除，除非规则显式标记为 fallback。
2. **P1：规则编辑未完整保存字段前缀。** `client/screens/rules/index.tsx:246-258` 未同步 `fieldPrefixes`；删除字段后旧前缀仍可能留在数据库，重新加回字段时复活。应保存完整规范化规则对象。
3. **P1：仓库改名只更新 warehouses 表。** `client/utils/database.ts:5844-5880` 没有级联更新业务表中的冗余 warehouse_name，也会破坏依名称查 ERP 仓库的逻辑。ERP 管理仓名称应锁定不可编辑；普通改名需事务化级联或只按 warehouse_id 关联。
4. **P2：仓库名称被限制为 4 个字符。** `client/screens/warehouse-management/index.tsx:91-97` 与输入框限制不适合未来正式仓名。
5. **P1：物料绑定历史更新不完整。** 型号/版本变更只更新部分新条件记录，旧型号历史可能保留；通用版本绑定与精确版本历史 join 也不一致。绑定应使用稳定 binding_id，历史记录保留扫描值并单独保存当时解析结果。
6. **P2：动态更新列缺少 allowlist。** `updateWarehouse`、`updateInventoryBinding` 等内部函数拼接字段名；即使当前调用可信，也应限制允许列。
7. **P1：设置页同步计数在上传成功前递增。** `client/screens/settings/index.tsx:654-846` 可能把失败尝试统计成成功导出；同时每次上传整库历史，造成重复快照和大文件。计数应在确认成功后提交，改为增量/按单据同步。
8. **P1：设置初始化缺少统一错误边界。** `loadData`、自动备份状态加载有未捕获异步失败，页面可能保留旧状态却看起来正常。增加统一 loading/error/retry 状态。
9. **P1：删除/编辑已同步单据不会同步修订电脑端 Excel。** UI 应明确“本地更正未同步”，并提供覆盖更新/撤销文件的任务。
10. **P2：首页“作业就绪”只基于仓库数量。** 应至少检查当前仓库、规则、必要绑定、目标账套启用状态和同步助手可用性；不要把数据库读取异常当成无数据。

## 6. 拆包打印、Excel、NAS 与同步助手

1. **P1：拆包打印没有可靠消费确认。** `markUnpackRecordsAsPrinted` 和 `addPrintHistory` 没有实际调用；同步助手 `/labels` 固定覆盖 `标签打印.xlsx`。连续两次拆包可能在打印程序读取前覆盖上一任务。
2. **P1：同步助手局域网接口无鉴权。** `scripts/label_sync_server.py:302` CORS 为 `*`，`:1003` 监听 `0.0.0.0`，同一网络设备可上传并覆盖文件。应使用首次配对令牌、来源限制和每设备撤销机制。
3. **P1：Excel 直接写最终路径，不是原子替换。** 打印程序/Excel 同时读取或进程崩溃时可能看到半个文件。应写 `.tmp`，fsync/关闭后 `os.replace` 到最终路径。
4. **P1：上传返回 HTTP 200 但业务失败。** 客户端若只看状态码会误判。业务错误应返回对应 4xx/5xx，并保留结构化错误码。
5. **P2：每次上传前都做 health 请求。** `client/utils/excel.ts:235` 使每次同步多一次 LAN 往返。缓存最近 30-60 秒成功健康状态，上传失败时再重探。
6. **P2：在 JS 线程生成整库 Excel+base64。** 大数据量会冻结扫码界面。改为按单据增量导出、后台任务或原生文件流上传。
7. **P2：缺少幂等请求和任务队列。** 推荐为每次打印/同步生成 `jobId`、内容 SHA-256、状态 `pending/received/printed/failed`；重复上传同一哈希只返回已有任务。
8. **P2：压缩 XLSX 只限制压缩包大小。** openpyxl 解压可能放大占用，应限制 sheet/row/cell 数和解压后估算大小。

### 同步助手优先优化路线

1. 配对令牌、设备列表、撤销与接口版本号。
2. 临时文件+原子替换，打印任务不再固定覆盖单文件。
3. jobId+SHA-256 幂等、明确回执和失败重试。
4. mDNS/局域网自动发现，减少手输 IP；保留手动地址回退。
5. 托盘状态页展示目标目录、最近任务、失败原因、当前版本和日志导出。
6. 前端按单据同步增量，设置页只做补偿重传，不反复导出全部历史。

## 7. expo-sqlite、持久化与备份审查

1. **P1：Web 数据库是内存 mock。** `client/utils/database.ts:1301` 附近的 Web 实现刷新即丢失。Web 预览只能验证界面和流程，不能用于判断 APK 持久化或备份正确性；界面应明确标注“临时测试数据”。
2. **P1：绑定表迁移不是显式事务。** `client/utils/database.ts:2377-2423` 依次 rename/create/copy/drop；中途崩溃可能留下 `inventory_bindings_legacy` 和不完整新表。用单事务并在启动时检测/恢复中间态。
3. **P1：原生后台备份使用硬编码 NAS 地址。** `AutoDatabaseBackupWorker.kt:481` 与 JS 设置读取的地址不是同一配置源，前台手动备份和后台备份可能发往不同服务器。用原生 SharedPreferences/桥接模块保存同一配置。
4. **P1：原生备份不创建 `/backup` 目录。** 新 NAS 目录不存在时可能长期 409。启动备份前执行 MKCOL 或明确初始化检查。
5. **P1：JS 文件上传没有统一超时。** `FileSystem.uploadAsync` 不受普通 fetch 超时控制，NAS 卡住时页面可能长时间等待。增加可取消任务和总时限。
6. **P1：409 冲突可能触发近千次重试。** 目录创建把 409 当成功，而文件上传 409 又继续递增序号；应区分目录已存在、文件冲突、权限失败，并先列目录或使用服务端分配文件名。
7. **P2：本地/缓存备份没有保留策略。** 文档目录和原生 cache 快照持续增长。建议保留最近 N 份、最近 N 天，并永远保留最后一份已验证备份。
8. **P2：每次写后 FULL checkpoint。** 全局写队列能降低锁冲突，但每次业务写都 checkpoint 会增加扫码保存延迟和 WAL 锁竞争。批量事务提交后或进入后台/备份前 checkpoint。
9. **P2：声明 foreign_keys 但没有实际外键。** 删除和改名完全依赖手工维护，容易出现孤儿行。核心关系逐步增加外键或集中 repository 事务。
10. **P2：删除归档覆盖不完整。** 出库/订单/仓库部分有归档，入库和盘点恢复能力不足。制定统一软删除/审计策略。
11. **P1：入库 traceNo 唯一性未按账套隔离。** 两家公司可能出现相同供应商追溯号；正式双账套应使用 `(erp_account_key, trace_no)` 组合唯一，并明确同账套重复规则。
12. **正向项**：JS 手动数据库导出在串行数据库操作和 WAL checkpoint 后复制，基本具备一致性；入库批量写和 trace 重复检查位于事务中；配置恢复的核心配置替换也使用了事务。

## 8. UI 视觉与全局设计规范

### 8.1 与预览图不一致的主要部分

1. **P2：圆角明显偏大。** 预览图主卡片约 8px；`client/constants/uiRedesign.ts:6` 使用 `BorderRadius.lg`，而 `client/constants/theme.ts:164-168` 的 lg 为 18px。`CustomAlert.tsx:103` 甚至达到 34px。建议统一：卡片 8px、输入框/按钮 6-8px、弹窗 10-12px、圆形图标按钮才使用 50%。
2. **P2：CSS 圆角注释与实际值不符。** `client/global.css:17` 基准 0.75rem 是 12px；`:260` 注释称 8px。需建立单一令牌源。
3. **P2：触控目标偏小。** `uiRedesign.ts:21-23` 的 34/36/40px 按钮低于 PDA 友好的 44-48px。视觉尺寸可紧凑，但可点击区域至少 44px。
4. **P2：存在两套颜色/圆角/阴影系统。** React Native theme 与 CSS/Uniwind 令牌语义不同，toast、订单页、规则页仍有硬编码颜色和 elevation。应只保留语义令牌：background/surface/text/muted/border/primary/success/warning/danger。
5. **P2：页面头部和弹窗实现不统一。** 部分使用 `UiWorkflowSummary`/公共 Modal，订单页等仍保留页面内自定义 Alert/Modal，导致间距、字体和按钮顺序不一致。
6. **P2：部分图标按钮缺少 accessibilityLabel/role。** 返回、删除、编辑、刷新等按钮需要 44px 点击区、可访问名称和 disabled 状态。
7. **P2：Modal 可用高度计算可能在键盘弹出时溢出。** `client/components/AppModalCard.tsx:37` 使用 `Math.max(windowHeight, screenHeight)`，应以当前可用窗口和 safe area 为准。
8. **P2：Screen 的键盘处理与注释不一致。** `client/components/Screen.tsx` 默认键盘状态未实际驱动部分分支，嵌套滚动检测也不能覆盖所有子树；长弹窗/小屏 PDA 仍有遮挡风险。
9. **P3：字体通过屏幕宽度分桶缩放。** `client/constants/responsive.ts` 的 `rf` 会让不同手机层级不一致；建议固定排版层级，只调整容器和每行数量。
10. **P3：静态 Proxy 缓存令牌不完全响应旋转/分屏。** `client/constants/theme.ts` 的模块级缓存可能保留旧尺寸。

### 8.2 页面级视觉结论

- **首页**：与预览图最接近，快捷作业卡片结构清晰；需要统一图标容器尺寸、去除重复 readiness 文案，并让大/小屏只改变网格列数和间距，不缩放字体。
- **扫码出库/入库/盘点**：扫码输入区应始终保持第一视觉焦点；顶部摘要只保留账套、单号、客户/供应商和进度。错误反馈采用声音+一行高对比提示，避免只靠 toast。
- **列表页**：同一层级列表项应统一 56/64px 最小高度、右侧操作图标位置和分割线；长规格型号最多两行并提供详情弹窗，不用单行截断隐藏关键信息。
- **弹窗**：主按钮固定右侧/底部，危险操作使用 danger 色；拆包数量等数值输入应默认全选并显示单位。
- **设置页**：按“ERP 对接、扫码规则、仓库与物料、同步与备份、系统”分组；每项显示状态和错误，不把测试按钮、开关、跳转混成同一交互样式。

静态审查无法验证真实设备上的文字重叠、键盘遮挡、焦点恢复、声音时序和不同 DPI 像素效果。这些属于后续真机验收项，而不是本轮通过编译可证明的内容。

## 9. 工程规范与可维护性

1. **P1：没有发现业务测试文件。** 规则解析、账套路由、拆包、盘点草稿、数据库迁移和备份都属于高风险逻辑，应优先补纯函数/SQLite 集成测试。
2. **P2：核心文件过大。** `client/utils/database.ts` 超过 9000 行，outbound/settings/inbound/orders/inventory 页面均为千行级；后端 ERP 与入口也过大。建议按 domain 拆分 repository、service、hook 和展示组件。
3. **P2：重复逻辑较多。** ERP 错误格式化、扫码数量校验、型号+版本规范化、同步状态更新、页面回焦和语音反馈应抽成共享服务/Hook，但不要创建过度抽象。
4. **P2：`any` 使用广泛。** ERP 返回、Excel 行、数据库写入等关键边界应使用 schema 校验和窄类型；类型断言不能替代运行时数据检查。
5. **P2：AsyncStorage key 有集中常量与散落字符串两种写法。** 双账套迁移时容易漏改，需统一命名并带 schemaVersion/accountKey。
6. **P2：读取函数吞错。** 部分函数数据库异常后返回 false/null/空数组，上层会误显示“未绑定/无数据”。数据不存在与数据库故障必须使用不同结果。
7. **P3：AuthContext 基本为空实现。** 若不使用应移除；若作为未来登录入口，应明确职责并避免给开发者造成已鉴权的错觉。
8. **P3：依赖中保留较多脚手架包。** 本轮未运行 depcheck，不能直接判定删除；后续应静态核对实际 import 后再精简。
9. **P2：生产日志需脱敏。** 扫码内容、单号、客户/供应商、ERP 上游响应和令牌不得进入 release console 或上传日志。

## 10. 建议补充的最小测试矩阵

1. 规则：相同分隔符、不同供应商条件；型号相同但版本不同；缺数量、非法数量、超大数量。
2. 双账套：相同 voucherCode、相同 traceNo、相同存货编码；A/B token 与 orgId 交叉注入必须失败。
3. 出库：新单/切换/恢复；缓存单据被作废；超量拆包；拆包提交中途失败；拆包行编辑。
4. 入库：II 单号导出不覆盖；未审核变审核/弃审消息乱序；最终确认时 ERP 明细变化。
5. 盘点：整包+拆包同时保存；切换类型后重复提交；10 次快速连扫后杀进程恢复。
6. SQLite：每一版迁移中途异常；恢复库迁移失败后回滚；WAL 有未 checkpoint 数据时备份。
7. NAS：断网、401、409、磁盘满、上传超时、连续同名任务、打印程序占用文件。
8. APK：云构建覆盖本地旧版升级；保留数据库；后台备份配置与前台设置一致。

## 11. 推荐修复顺序

### 第一阶段：数据与账套安全

1. 修复盘点双草稿重复保存。
2. 修复 II 单号导出文件名。
3. 修复数据库恢复回滚和 Android 备份快照/签名。
4. 统一 Android 包名和签名升级链。

### 第二阶段：后端正式化

### 第三阶段：业务一致性

1. 出库 ERP 恢复失败阻断、状态校验和最终确认刷新。

4. 修正规则硬条件、仓库改名和物料绑定历史逻辑。

### 第四阶段：同步助手与 UI

1. 同步助手配对、原子写、幂等 job 和打印回执。
2. 增量导出与后台生成，减少前端卡顿。

4. 用真机矩阵验收小屏/大屏、键盘、焦点、声音和无障碍。
