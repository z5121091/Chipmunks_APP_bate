## 1. 需要处理的问题

### 1.1 P2：盘点缺少已在其他扫码模块实施的供应商归属校验

位置：`client/screens/inventory/index.tsx:715`、`:752`、`:799`。

盘点在检测解析规则后直接按型号、版本取得存货编码并保存草稿，没有调用 `assertRuleSupplierForScan`。出库、入库和补打分别在 `client/screens/outbound/index.tsx:2371`、`client/screens/inbound/index.tsx:1028`、`client/utils/labelReprint.ts:227` 调用该校验。

触发条件：规则通过 `supplierId` 明确关联供应商 A，而其解析得到的物料绑定到供应商 B。出入库和补打会拒绝，该盘点路径仍可计入记录。规则未配置关联或物料供应商未知的旧行为，不应因为修复而被强制收紧。

影响：跨模块业务校验不一致，配置错误时可能把错误规则解析出的结果计入盘点。库存查询也没有该调用，但它是只读功能，是否增加同样拦截需单独明确产品边界，不与盘点写入问题混为一谈。

建议：先补盘点校验及相同／不同／未知供应商、内部标签绕过、迟到响应不落草稿的回归。当前源码证据可确认遗漏；本轮没有在真实 PDA 写入测试盘点单。

### 1.2 P2：部分弹窗的最小高度可超过可用窗口

位置：`client/components/AppModalCard.tsx:45-61`；调用方 `client/screens/inventory-binding/index.tsx:793`、`client/screens/inventory-binding/SupplierManager.tsx:180`；样式 `client/screens/inventory-binding/styles.ts:289-300`。

`form` 最小高度 340，`largeForm` 最小高度 420，未再按实际可用窗口封顶。物料绑定、供应商弹窗外层为普通居中容器，其卡片样式只有宽度约束，没有 `maxHeight`。窗口高度 320 dp 时，420 dp 卡片及外边距无法完整进入视口，正文内部滚动也不能解决固定头尾超界。

范围：当前 Android 配置锁定竖屏，不能把普通 PDA 横屏作为已复现事实。该约束问题对 Web 小高度窗口可由源码直接推导；Android 多窗口或键盘影响需要目标设备验证。

已排除：出库拆包卡片已有 `maxHeight: '84%'`；内部建标弹窗已有键盘及实际视口高度处理，不应笼统算成同一遗漏。

建议：基于实际容器可用高度限制卡片，保证固定操作区可达；需要时由正文滚动承载内容。不要只缩小字体或继续叠加固定高度。

### 1.3 P2：窗口变化后，部分响应式样式仍使用初始尺寸

位置：`client/screens/orders/index.tsx:53`、`client/screens/orders/styles.ts:9`、`client/screens/inventory-binding/index.tsx:48`、`client/screens/inventory-binding/styles.ts:8`；底层 `client/constants/theme.ts:122`、`:329-362`。

页面通过 `useMemo(() => createStyles(theme), [theme])` 缓存样式，但 `createStyles` 内部读取 `Dimensions.get('window')` 计算 compact 档位，窗口变化并不会使该 memo 失效。底层 `Spacing`、圆角、边框、排版 Proxy 首次读取后也缓存，`isSmallScreen` 更在模块加载时固定。

触发条件：Web 预览先以窄窗口打开，再拉宽，或相反；以及设备实际窗口可用尺寸发生变化。相同目标尺寸可能因首开尺寸不同而得到不同的间距、字号或紧凑分支。

影响：局部容器更新了宽度，部分子样式仍停留在旧档位，是反复出现大小屏适配不一致的系统性原因。

建议：统一尺寸订阅与样式依赖；组件使用的响应式 tokens 也应具有明确更新方式。避免只给个别页面添加 `useWindowDimensions`，底层 tokens 却继续静态缓存。

### 1.4 P2 布局风险：间距无上限放大，固定宽度弹窗里的长按钮反而更挤

位置：`client/utils/responsive.ts:40-47`、`client/constants/theme.ts:128`、`client/components/UiRedesign.tsx:531-554`；具体文案 `client/screens/label-reprint/InternalLabelForm.tsx:128`。

间距按 `min(width/375, height/667)` 线性放大，无最大系数；字体大屏只温和放大约 6%，弹窗最大宽度却固定 400 dp，工具按钮高度固定。以 1024×1366 dp 首开估算，`Spacing.md` 约 32.8，双按钮页脚的单个按钮宽约 157，扣两侧内边距、图标和 gap 后，文字槽不足 70 dp。

“确认另建并打印”共七个汉字。系统字体 1.3 倍时，即使允许缩到 0.78，仍大约需要 105 dp。该组合存在明确尺寸预算冲突。最终是裁切、溢出还是额外缩放，需要真实渲染核对；本轮没有取得应用页面截图，不能标记为已观察到的 PDA 现象。

建议：按容器宽度约束 padding/gap；长动作允许调整布局或独占一行。不要靠增加整个卡片宽度或压小全局字体来掩盖问题。

### 1.5 验证问题：客户端全量 Jest 的断言通过，但进程退出码不是零

本轮全量输出：105/105 套、1512/1512 项断言通过，但进程退出码为 1。日志出现 `Cannot log after tests are done`，堆栈涉及 Expo 懒加载的 `fetch`、原生 JS logger 及测试环境收尾。

影响：不能把当前结果描述为“全量检查全绿”，也会影响 CI 的成功判定。尚无证据据此认定 PDA 的热更新功能异常。

建议：单独处理测试环境收尾，补足 fetch/Expo mock 或清理时序，修复后再以完整命令和退出码复核；不要使用 `--forceExit` 隐藏异常。

## 2. 按钮反复过大、错位的原因

1. `AnimatedButton` 的外层 `Animated.View` 接受 `containerStyle`，内层触摸区接受 `style` 且默认 `width: '100%'`。宽度、flex 设错层容易造成与父布局不一致。现有补打顶部、供应商添加区等部分调用已经正确约束，不能报成全部仍坏，但该契约仍容易在新增按钮时误用。
2. 间距／图标、字体、按钮高度、弹窗宽度混用不同的缩放策略，没有统一的尺寸预算。
3. 只检查按钮本身，没有核算父容器、外层包装、padding、gap、图标、最长文案、字体缩放及键盘可用高度。
4. 把编译和交互单测通过当成 UI 达标。物料绑定与供应商测试 mock 了真实 styles、AppModalCard 或按钮，它们不会执行真实 Yoga／字体布局，也无法证明文字不被截断。

后续 UI 修改应采用的完成条件：

- 先区分同行工具按钮、主操作按钮和“移除”这类短文字动作，不统一套全宽或 `flex: 1`。
- 明确宽高约束施加在外层还是内层，复用现有组件和已验证的父布局。
- 至少覆盖 320/360 dp 小屏、600/768/1024 dp 大屏、系统字体 1.0/1.3、长文案及键盘场景。
- 同时核对窄屏冷启动、大屏冷启动、从窄拉宽／从宽缩窄；用真实页面渲染确认关键操作完整可见。
- 共用组件变更按页面逐类回归，不在没有整体验证时全局替换。
