## 2. 已实现项一：旧“规则占位字段”退役

用户在数据库发现“规则占位字段”表，认为当前已通过忽略段替代，询问是否需要移除。

退役前核对的情况：

- 当前解析规则通过 `ignore:N` 及“添加忽略段／忽略此段”处理不提取为标准业务字段的分段。
- 旧占位字段规则读取、初始化及旧配置恢复时有迁移兼容逻辑。
- 全局占位字段定义表和无生产调用的旧管理函数仍有残留。
- 当前初始化仍创建旧表，完整数据库恢复校验仍要求旧表存在，不能只手工删除数据库中的表。
- 历史业务记录的 `customFields` 数据与全局定义表不同，不应因清理定义表而连带删除。

已实施处理：

- 新库不再创建旧定义表，清理对应表映射、Web 模拟表、废弃管理函数及未使用的文案和样式。
- 初始化时先把旧规则转换为忽略段，再在同一事务中删除中文“规则占位字段”和英文 `custom_fields` 两种旧表；转换失败则整体回滚。
- 完整数据库恢复不再要求旧定义表存在，兼容有旧表的老备份及无旧表的新备份。
- 配置 JSON 继续接受旧字段定义并转换关联规则，新导出保留空 `customFields` 作为格式兼容；统计不再读取已退役表。
- 保留历史业务记录中的 `customFields` 数据和旧链接跳转，不改当前解析、识别、拆包或打印规则。
- 原生自动备份不依赖旧定义表，本次没有修改原生模块。

## 3. 待评估项二：超过八个标准字段的动态标签与拆包

使用场景：用户有一种十段标签，每段都有数据，额外数据随型号变化。以前部分超过标准字段的段是固定值，预设模板可以补回；新情况不能依赖固定值。用户曾询问是否增加字段。

本次源码核对的情况，后续应重新验证：

- 八个标准业务字段是型号、批次、封装、版本号、数量、生产日期、追溯码、箱号；不是二维码总段数只能为八段。
- 额外段可以配置为忽略段，扫描原文可保留这些数据，但它们不会提取到标准业务字段。
- 普通拆包与部分箱号拆包仍依赖供应商模板和标准字段重建二维码，不能保证额外动态段完整传递。
- 补打修改数量已有按原文字段位置修改的工具，可以作为未来技术参考，但并未使所有拆包模板自动具备该能力。

候选方向仅供以后评估：

1. 在明确供应商、完整原码、各段含义和实际标签版式后，决定扩展预设模板、增加规则内扩展字段或其他实现。
2. 如果采用保留原码生成子标签，仍需把每张子标签的数量、已分配的追溯码或箱号、包装身份、打印任务和补打重试贯通校验。
3. 额外字段需不需要展示、导出、参与识别或打印为文字，应按实际需求确定，不能一概增加固定值或标准业务列。
4. 继续保持现有标签及包装识别行为，不凭空更改原厂字段或无码业务规则。
