- 当前决定：**暂缓实施。用户认为现阶段收益不大，先保存讨论，后续有需要再评估。**
- 实施状态：本文涉及的双电脑分流功能尚未开发。本文是方案记录，不代表功能已经实现，也不构成开发、构建、发布热更新或推送 Git 的授权。

## 1. 使用背景与目的

仓库有两名作业人员，各负责一个 ERP 账套、各使用一台 Windows 电脑，共用一台 PDA。

当前 PDA 只配置了一套同步助手连接地址，单据文件集中发送到同一台电脑。讨论希望同事能直接在自己的电脑收到所属账套的单据，减少找文件、转发文件和依赖另一台电脑开机的情况。

打印机继续由上海花栗鼠这台电脑承担。用户不要求通过本方案增加第二台打印电脑，也不要求两台电脑自动互相备份。

## 2. 当前实现情况

以下是本次讨论时核对源码得到的情况，后续继续前应重新确认：

1. APP 的 `SyncConfig` 目前是一组 IP、端口及可选配对密钥，多个同步和打印入口使用同一套连接配置。
2. 电脑端已有入库、出库、盘点 Excel 接收接口，支持配对校验、临时文件处理、原子保存及按仓库归档。
3. 这三个接收接口虽然已经接受 `erp_account_key` 参数，但目前没有基于它做账套路由或接收范围校验；已核对的 APP 导出入口主要传递仓库信息，尚未完整传递和使用明确的账套归属。
4. 普通单据没有主从分发队列或完整的传输回执去重机制。标签打印已有自己的任务标识及防重复机制，不能直接等同于普通文件分发。
5. 另一台电脑可以部署同一版同步助手。需要扩展的主要是 APP 的连接配置与目标选择，不必因为两台电脑而另做一个“从机程序”。
6. 按仓库导出的出库历史可能涉及多个账套，不能仅凭仓库名称决定文件应发给哪台电脑。

## 3. 曾讨论的两个方向

| 方向 | 数据流 | 主要代价与限制 |
|---|---|---|
| 主机、从机分发 | PDA 全部发主机，主机再向同事电脑分发指定账套文件 | 需要后台分发、持久待发任务、离线补收、回执去重和文件版本顺序控制；主机仍须开机 |
| APP 按账套直发两台电脑 | PDA 根据单据所属账套选择对应同步助手 | 需要改 APP 的双连接配置、单据路由、打印路由和连接状态；两台电脑可独立接收自己的单据 |

**讨论认可的优先方向是第二种。** 没有选择主从转发作为当前优先方案，但第二种也已经决定暂缓，不立即实施。

## 4. 保留的设计方向

### 4.1 两套独立配置，固定一个打印目标

设置中的“同步助手”可以使用现有界面元素，分成两个配置区：

| 配置名称 | 职责 |
|---|---|
| 上海花栗鼠同步助手 | 接收上海花栗鼠账套的单据，承担两个账套的标签打印 |
| 无锡笃能同步助手 | 接收无锡笃能账套的单据 |

每个配置区分别保存 IP、端口、配对密钥，支持扫描对应电脑的连接二维码，并显示各自连接状态。可以固定显示“标签打印由上海花栗鼠同步助手处理”，第一版不增加主副机切换或通用打印目标选择器。

两台电脑运行同一版同步助手，不设置主从转发关系。APP 每次只向该操作对应的目标发送，不向两台电脑广播同一份单据。

### 4.2 单据与打印的目标

| 操作 | 目标电脑 |
|---|---|
| 上海花栗鼠账套的入库单、盘点单、出库历史文件 | 上海花栗鼠电脑 |
| 无锡笃能账套的入库单、盘点单、出库历史文件 | 无锡笃能电脑 |
| 任意账套的标签补打、修改数量打印、新建内部标签、拆包和剩余标签打印 | 统一为上海花栗鼠电脑 |

账套和仓库应保持区分。当前上海花栗鼠的默认作业仓库是“无锡总仓”，无锡笃能的默认作业仓库是“无锡仓库”，但不能把这两个仓库名称当成永久的账套路由规则。以后新增仓库时，仍以单据所属账套确定接收电脑，以单据实际仓库确定归档目录。

本方案不涉及转发 ERP 凭证、APP 数据库或在两台电脑间复制配对密钥。

### 4.3 离线行为

| 上海花栗鼠电脑 | 无锡笃能电脑 | 预期行为 |
|---|---|---|
| 在线 | 在线 | 各自接收本账套单据，所有标签发上海花栗鼠打印 |
| 离线 | 在线 | 无锡单据仍能同步；上海单据不能同步；两个账套都不能打印标签 |
| 在线 | 离线 | 上海单据与标签打印正常；无锡单据不能同步，不自动改发上海电脑 |
| 离线 | 离线 | 不能向电脑交付单据或打印；保留已有本地作业记录及待处理状态 |

打印电脑离线时，明确提示检查上海花栗鼠同步助手，不能显示“已打印”。原有打印任务应保留，恢复后从原入口重试，并继续使用原任务标识防重复。

**电脑恢复后是否自动补传尚未确定。** 不能把“之后可以从记录入口重试”写成“当前已经有自动补传功能”。

## 5. 实施规模和风险

本方案属于中等规模改动，主要改动在 APP，不是只修改电脑端同步助手，也不是简单再增加一个 IP 输入框。

主要涉及：

1. 两套连接配置、配对信息、连接二维码录入和独立连接状态。
2. 原有单地址配置的迁移与兼容。
3. 入库、盘点、出库历史，以及历史记录再次导出的账套归属。
4. 全部标签打印入口的固定目标、任务重试和电脑端会话核对。
5. 不同电脑离线时，分别反馈单据接收状态和打印状态。

重点风险包括：

- 用户切换账套后，旧异步请求被错误发送到新目标。
- 以当前页面选中的账套代替历史单据实际所属账套。
- 混合账套的历史文件被整份发送给某一台电脑。
- 打印地址随账套切换，误发到只负责接收数据的电脑。
- 迁移时丢失原有连接或配对密钥。
- 重试时生成新打印任务，造成重复出纸。
- 一台电脑在线，被界面误显示成所有同步和打印功能都可用。

按讨论中的技术方向，APP 侧主要是配置、界面和请求路由，预计可以考虑使用现有热更新机制；但必须以实际开发后的兼容性检查为准，不能提前保证一定无需重建 APK。电脑端若修改通知或接收校验，需要重新构建同步助手 EXE。

## 6. 为什么暂缓，以及何时值得重新评估

用户认为现阶段收益不大，希望避免为使用频率有限的需求扩展连接与业务逻辑，因此先不实施。

如果同事每天都需要自己账套的单据，经常依赖本人电脑开机、查找或转发文件，这个方案能减少日常配合成本，值得重新评估。

如果只是偶尔需要表格，现有转发方式基本够用，则继续保持当前稳定流程。该方案不会消除上海花栗鼠打印电脑必须开机的要求。

还要注意：两台电脑各自收文件后，上海花栗鼠电脑不会自然拥有另一账套的全部文件；若仍要求集中留档，需要另定备份方式。

## 7. 后续恢复评估时仍需确定的事项

- 是否把原来的连接配置自动继承到上海花栗鼠配置，如何处理旧配置和回退兼容。
- 对没有记录账套的历史单据，如何明确归属，不能静默猜测。
- 按仓库导出的历史出库数据包含多个账套时，是否按账套拆成文件后分别发送。
- 离线后使用现有手动导出补传，还是另加自动待发送队列。
- 是否要求一台电脑集中保留两个账套的文件副本。
- 电脑端是否增加接收账套限制，以及怎样防止误配地址后仍然收错数据。

重新开始前，应先逐项核对这些需求及当前源码，再形成当时的实施清单。

## 8. 后续实施的验收场景

仅作为未来验收清单，本轮没有执行以下新功能验收：

- 两个账套各完成一次入库、盘点及出库历史导出，只有指定电脑收到对应文件。
- 从历史记录重发旧单据，发送目标不受当前页面账套切换影响。
- 同步过程中切换账套、离开页面，再返回，旧响应不覆盖另一账套状态。
- 分别关闭一台电脑和同时关闭两台电脑，单据与打印状态符合离线表格。
- 在无锡账套补打、新建内部标签及拆包，标签始终发到上海花栗鼠电脑。
- 打印提交失败或结果不明时，从原任务重试，不重复生成任务或重复出纸。
- 升级前已有地址、密钥和打印任务能够保留。
- 混合账套和缺少账套的历史数据按确认后的规则处理。
- 归档目录、文件名及既有单据内容不因连接配置改造被意外改变。

## 9. 独立相关需求：点击通知打开文件

这项需求与双电脑分流可以独立实现。此前用户已经认可方向，**但目前尚未实现**，不能记为已交付；本次仅整理文档，不推进功能开发。

认可的范围和交互：

- 对入库单、盘点单、扫码出库单的成功通知增加点击动作。
- 单份文件优先用系统关联的 Excel／WPS 打开。
- 打开失败时回退到所在文件夹；文件已移动或删除时，提示并尝试打开原目录。
- 合并多份文件时打开对应目录，避免一下打开多个表格。
- 建议按仓库与单据类型合并通知，避免一条通知涉及多个目录。
- 每条通知绑定自己的真实落盘文件，不能只记录一个全局“最新文件”，避免点击旧通知打开新文件。
- 失败通知不绑定成功文件的打开动作。
- 拆包、标签补打等标签类通知暂不增加文件点击动作。

讨论时的实现是 `pystray` 文字通知，通知事件没有传递真实文件路径或点击动作；通知还会合并连续同步结果。因此需要补充可靠的通知与文件关联，不能只给托盘图标加一个“打开最近文件”的回调。

若要求 Windows 通知中心中的每条旧通知都准确打开对应文件，应选择能够为每条通知提供独立激活信息的实现；不能在尚未验证时承诺旧气泡接口支持该行为。

这项主要影响电脑端同步助手，和双电脑方案的暂缓状态分别管理。以后继续时仍需确认当时的需求与实施范围；不要自动把“双电脑暂缓”解释成“通知点击已取消”，也不要把本文当成现在推进开发的授权。
